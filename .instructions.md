# Next.js 15 Full-Stack Web Application Development Guide

**AI Assistant Instructions for Copilot**

## 1. Project Overview

This is a modern, full-stack web application built with:
- **Framework**: Next.js 15 with App Router
- **UI Library**: React 19 with React Compiler
- **Database**: PostgreSQL 16 (Docker)
- **ORM**: Drizzle ORM
- **Styling**: SCSS Modules
- **State Management**: Zustand (UI state) + TanStack Query v5 (server state)
- **Validation**: Zod
- **Language**: TypeScript
- **Code Quality**: Biome (linting & formatting)

### Tech Stack Summary
```
Frontend: React 19 + Next.js 15 (App Router)
Backend: Node.js with Next.js Server Actions
Database: PostgreSQL 16 with Drizzle ORM
State Management: Zustand + TanStack Query
Styling: SCSS Modules
Validation: Zod Schemas
Runtime: Node.js with TypeScript
Package Manager: pnpm (workspace)
```

## 3. Core Development Rules

### 3.1 React 19 & React Compiler

**Rules:**
1. **NO manual optimization hooks** – Do NOT use `useMemo`, `useCallback`, or `React.memo`
2. **Server Components by default** – All components in `src/app/` and `src/components/` are Server Components
3. **Use `'use client'` ONLY when:**
   - Component needs local state (`useState`, `useReducer`)
   - Component has event listeners (`onClick`, `onChange`, `onSubmit`)
   - Component uses client-side hooks (`useStore`, `useRouter`, `useParams`)
   - Component accesses browser APIs (`window`, `localStorage`)
4. **Isolate interactive parts** – Keep Server Components as wrappers, extract interactive logic into smallest `'use client'` sub-components

**Example:**
```typescript
// ✅ Good: Server component wrapping client component
export default function LoginPage() {
  return (
    <div>
      <h1>Login</h1>
      <LoginForm /> {/* 'use client' component */}
    </div>
  );
}

// ✅ Good: Only LoginForm is 'use client'
'use client';
export function LoginForm() {
  const [email, setEmail] = useState('');
  return <form><input onChange={(e) => setEmail(e.target.value)} /></form>;
}
```

### 3.2 Server Actions & Data Mutations

**Rules:**
1. **Location**: `src/actions/<feature>.ts`
2. **Directive**: MUST include `'use server'` at top of file
3. **Response Format**: ALL actions return `ActionResult<T>`:
   ```typescript
   export type ActionResult<T> = 
     | { success: true; data: T }
     | { success: false; error: string };
   ```
4. **Validation**: ALWAYS validate input with Zod BEFORE database operations
5. **Error Handling**: Catch ALL exceptions and return user-friendly error messages (never expose raw DB errors)

**Example:**
```typescript
'use server';

import { loginSchema } from '@/lib/zod/auth';
import type { ActionResult } from '@/actions/auth.actions';
import type { UserSession } from '@/types/user';

export async function loginAction(input: unknown): Promise<ActionResult<UserSession['user']>> {
  try {
    const validated = loginSchema.parse(input); // Zod validation first
    
    const user = await db.query.users.findFirst({
      where: eq(users.email, validated.email),
    });

    if (!user) {
      return { success: false, error: 'User not found' };
    }

    // Hash comparison, session creation, etc.
    return { success: true, data: { id: user.id, name: user.name, email: user.email, role: user.role } };
  } catch (error) {
    if (error instanceof Error) {
      return { success: false, error: error.message };
    }
    return { success: false, error: 'Login failed. Please try again.' };
  }
}
```

### 3.3 State Management

**Clear Responsibility Separation:**

1. **Server State / API Caching** → **TanStack Query v5**
   - Use `useQuery()` for data fetching
   - Use `useMutation()` for mutations (DEPRECATED – use Server Actions instead)
   - NOT for storing persistent application state

2. **Client UI State** → **Zustand**
   - Sidebar collapsed/expanded state
   - Modal visibility toggles
   - Active tabs, filters, sorting preferences
   - Search input values (temporary)
   - DO NOT store API response data here

**Zustand Store Location**: `src/stores/<feature>-store.ts`
**Naming Convention**: `use<Feature>Store`

**Example:**
```typescript
// ✅ Good: Zustand for UI state
'use client';
import { create } from 'zustand';

interface DashboardState {
  sidebarCollapsed: boolean;
  activeTab: string;
  toggleSidebar: () => void;
  setActiveTab: (tab: string) => void;
}

export const useDashboardStore = create<DashboardState>((set) => ({
  sidebarCollapsed: false,
  activeTab: 'overview',
  toggleSidebar: () => set((state) => ({ sidebarCollapsed: !state.sidebarCollapsed })),
  setActiveTab: (tab) => set({ activeTab: tab }),
}));
```

### 3.4 SCSS Modules & Styling

**Rules:**
1. **SCSS Modules ONLY** – Use `*.module.scss` extension for component-specific styles
2. **NO hardcoded values** – Always use design tokens from `src/styles/_variables.scss`
3. **Import variables & mixins**:
   ```scss
   @use '@/styles/variables' as *;
   @use '@/styles/mixins' as *;
   ```
4. **Conditional classes** – Use `clsx` utility for joining classes
5. **Responsive design** – Use breakpoints from `_variables.scss`: `$breakpoint-md`, `$breakpoint-lg`, etc.

**Example:**
```scss
// ✅ Good: Using variables and mixins
@use '@/styles/variables' as *;
@use '@/styles/mixins' as *;

.button {
  padding: 0.75rem 1.5rem;
  background-color: $primary-color;
  border-radius: $border-radius;
  color: #fff;
  font-weight: 600;
  transition: all 0.2s ease;

  &:hover {
    background-color: $primary-hover;
    transform: translateY(-2px);
  }

  @media (max-width: $breakpoint-md) {
    padding: 0.5rem 1rem;
  }
}

// ✅ Good: Conditional classes
import clsx from 'clsx';
import styles from './button.module.scss';

export function Button({ variant = 'primary', disabled = false }) {
  return (
    <button className={clsx(styles.button, {
      [styles.primary]: variant === 'primary',
      [styles.secondary]: variant === 'secondary',
      [styles.disabled]: disabled,
    })}>
      Click me
    </button>
  );
}
```

### 3.5 Zod Validation

**Rules:**
1. **Location**: `src/lib/zod/<feature>.ts`
2. **Naming**: Export types with `<Feature>Input` suffix
3. **Use before server actions**: Validate BEFORE any database operations
4. **Export schema AND type**: For both runtime validation and TypeScript inference

**Example:**
```typescript
// src/lib/zod/auth.ts
import { z } from 'zod';

export const loginSchema = z.object({
  email: z.string().email('Invalid email address'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
});

export type LoginInput = z.infer<typeof loginSchema>;

export const registerSchema = z.object({
  name: z.string().min(2, 'Name must be at least 2 characters'),
  email: z.string().email('Invalid email address'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
  confirmPassword: z.string(),
}).refine((data) => data.password === data.confirmPassword, {
  message: "Passwords don't match",
  path: ["confirmPassword"],
});

export type RegisterInput = z.infer<typeof registerSchema>;
```

### 3.6 Drizzle ORM & Database

**Rules:**
1. **Schema location**: `src/lib/db/schema.ts`
2. **Client location**: `src/lib/db/index.ts`
3. **Query patterns**:
   - Use `db.query` for reads (preferred – optimized)
   - Use `db.insert()`, `db.update()`, `db.delete()` for mutations
   - Use `.returning()` to get modified rows
4. **Always select specific columns** – Don't use `*` or select sensitive fields

**Example:**
```typescript
// src/lib/db/schema.ts
import { pgTable, text, timestamp, varchar } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';

export const users = pgTable('users', {
  id: varchar('id', { length: 36 }).primaryKey(),
  name: varchar('name', { length: 255 }).notNull(),
  email: varchar('email', { length: 255 }).unique().notNull(),
  passwordHash: text('password_hash').notNull(),
  role: varchar('role', { length: 50 }).default('user'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
});

export const usersRelations = relations(users, ({ many }) => ({
  posts: many(posts),
}));

// src/actions/auth.actions.ts
const user = await db.query.users.findFirst({
  where: eq(users.email, email),
  columns: { id: true, name: true, email: true, role: true }, // Only select needed columns
});
```

### 3.7 TypeScript

**Rules:**
1. **Strict mode enabled** (`"strict": true` in tsconfig.json)
2. **Always type function parameters and returns**:
   ```typescript
   export async function getUser(id: string): Promise<User | null> {
     // ...
   }
   ```
3. **Use interfaces for component props**:
   ```typescript
   interface ButtonProps {
     label: string;
     onClick?: () => void;
     disabled?: boolean;
   }
   ```
4. **Global types location**: `src/types/<feature>.ts`
5. **Avoid `any`** – Use `unknown` with proper type narrowing instead

## 4. Feature Development Workflow

When creating a new feature, execute these steps **sequentially**:

### Step 1: Type Definitions
- **File**: `src/types/<feature>.ts`
- Define interfaces and types the feature needs
- Export from this single source of truth

### Step 2: Static Constants
- **File**: `src/constants/<feature>.ts`
- Define route paths, navigation items, dropdown options
- Keep static configuration separate from runtime code

### Step 3: Database Schema (if data-persistent)
- **File**: `src/lib/db/schema.ts`
- Create/update Drizzle tables
- Define relationships
- Run migrations: `npm run db:push` (Drizzle)

### Step 4: Zod Validation Schemas
- **File**: `src/lib/zod/<feature>.ts`
- Define validation schemas for all input
- Export inferred types

### Step 5: Server Actions
- **File**: `src/actions/<feature>.actions.ts`
- Implement data mutations
- Integrate Zod validation and Drizzle queries
- Return `ActionResult<T>` pattern

### Step 6: Zustand Store (if UI state needed)
- **File**: `src/stores/<feature>-store.ts`
- Define UI state store
- Use `'use client'` directive
- Implement state setters and computed properties

### Step 7: UI Components & Styling
- **Location**: `src/components/features/<feature>/`
- Create feature components with `*.module.scss` styles
- Import and use Zustand stores
- Call server actions from `'use client'` components

### Step 8: Page Routes
- **Location**: `src/app/<feature>/page.tsx`
- Assemble components into pages
- Use layout wrappers (`DashboardLayout`, etc.)

## 5. Code Examples & Patterns

### 5.1 Creating a Server Action with Validation

```typescript
// src/lib/zod/post.ts
import { z } from 'zod';

export const createPostSchema = z.object({
  title: z.string().min(5, 'Title must be at least 5 characters'),
  content: z.string().min(50, 'Content must be at least 50 characters'),
  published: z.boolean().default(false),
});

export type CreatePostInput = z.infer<typeof createPostSchema>;

// src/actions/post.actions.ts
'use server';

import { createPostSchema } from '@/lib/zod/post';
import { db } from '@/lib/db';
import { posts } from '@/lib/db/schema';
import type { ActionResult } from './auth.actions';

export async function createPostAction(
  input: unknown,
  userId: string
): Promise<ActionResult<{ postId: string }>> {
  try {
    const validated = createPostSchema.parse(input);

    const [newPost] = await db
      .insert(posts)
      .values({
        id: crypto.randomUUID(),
        title: validated.title,
        content: validated.content,
        published: validated.published,
        authorId: userId,
        createdAt: new Date(),
      })
      .returning({ id: posts.id });

    return { success: true, data: { postId: newPost.id } };
  } catch (error) {
    if (error instanceof Error) {
      return { success: false, error: error.message };
    }
    return { success: false, error: 'Failed to create post' };
  }
}
```

### 5.2 Using Server Actions in Client Component

```typescript
// src/components/features/posts/create-post-form.tsx
'use client';

import { useState } from 'react';
import { createPostAction } from '@/actions/post.actions';
import styles from './create-post-form.module.scss';

export function CreatePostForm({ userId }: { userId: string }) {
  const [title, setTitle] = useState('');
  const [content, setContent] = useState('');
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault();
    setLoading(true);
    setError(null);

    const result = await createPostAction({ title, content, published: true }, userId);

    if (result.success) {
      setTitle('');
      setContent('');
      // Redirect or refresh
    } else {
      setError(result.error);
    }

    setLoading(false);
  };

  return (
    <form onSubmit={handleSubmit} className={styles.form}>
      <input
        type="text"
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="Post title"
        className={styles.input}
      />
      <textarea
        value={content}
        onChange={(e) => setContent(e.target.value)}
        placeholder="Post content"
        className={styles.textarea}
      />
      {error && <div className={styles.error}>{error}</div>}
      <button type="submit" disabled={loading} className={styles.button}>
        {loading ? 'Creating...' : 'Create Post'}
      </button>
    </form>
  );
}
```

### 5.3 Using Zustand Store

```typescript
// src/stores/modal-store.ts
'use client';

import { create } from 'zustand';

interface ModalState {
  isOpen: boolean;
  modalType: 'createPost' | 'editPost' | null;
  selectedPostId: string | null;
  open: (type: ModalState['modalType'], postId?: string) => void;
  close: () => void;
}

export const useModalStore = create<ModalState>((set) => ({
  isOpen: false,
  modalType: null,
  selectedPostId: null,
  open: (type, postId) => set({ isOpen: true, modalType: type, selectedPostId: postId || null }),
  close: () => set({ isOpen: false, modalType: null, selectedPostId: null }),
}));

// Usage in component
'use client';
import { useModalStore } from '@/stores/modal-store';

export function PostCard({ postId }: { postId: string }) {
  const { open } = useModalStore();

  return (
    <div>
      <h3>Post Title</h3>
      <button onClick={() => open('editPost', postId)}>Edit</button>
    </div>
  );
}
```

## 7. MCP (Model Context Protocol) Servers

### Available MCP Servers

**PostgreSQL MCP** – Query and manage database
- **Command**: npx @modelcontextprotocol/server-postgres
- **Environment**: `DATABASE_URL="postgresql://user:pass@localhost:5432/db"`
- **Use cases**: Check schema, run queries, verify data integrity

**Puppeteer MCP** – Browser automation
- **Use cases**: Screenshots, web testing, E2E testing

**Playwright MCP** – Advanced browser automation
- **Use cases**: Multi-browser testing, visual regression testing

**GitHub MCP** – GitHub integration
- **Use cases**: Fetch repo info, search code, manage issues/PRs
- **Setup**: Add GitHub PAT in `.vscode/mcp.json`

### Configuration

MCP servers are configured in `.vscode/mcp.json`:

```json
{
  "servers": {
    "postgres": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-postgres",
        "postgresql://postgres:password@localhost:5432/my_app_db"
      ]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${input:githubToken}"
      }
    }
  }
}
```

1. Define Zod schema in `src/lib/zod/<feature>.ts`

1. Add table definition to `src/lib/db/schema.ts`

3. Run `npm run db:push` to apply

## 9. Best Practices & Dos/Don'ts

### ✅ DO

- Write TypeScript with strict mode enabled
- Use Server Components by default
- Validate all inputs with Zod before DB operations
- Return `ActionResult` from all server actions
- Use SCSS modules for component styles
- Keep stores UI-state-only
- Separate concerns: types → constants → schema → actions → components
- Use design tokens (`$primary-color`, etc.) in SCSS
- Test responsive design at breakpoints

### ❌ DON'T

- Use manual optimization hooks (`useMemo`, `useCallback`)
- Bypass Zod validation
- Store API response data in Zustand
- Hardcode colors, sizes, or breakpoints in SCSS
- Use inline styles (except temporary testing)
- Expose raw database errors to users
- Mix server and client logic in same component
- Use `any` type
- Create files outside the strict folder structure
